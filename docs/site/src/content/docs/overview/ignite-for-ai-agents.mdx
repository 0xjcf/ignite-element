Ignite Element gives agents a behavior contract instead of asking them to scrape
the DOM. The same `igniteCore(...)` value that registers a custom element also
exposes a headless runtime with commands, derived states, emitted events,
and agent-readable metadata.

That contract is useful because it is the same surface for humans, tests, and
tools:

- Humans click the custom element and see the renderer view.
- Tests call the runtime directly and assert native snapshots, derived states, and events.
- Agents inspect minimal `get('schema')` discovery and projected availability, call `execute()`, and
  observe outcomes through `on(...)` or `watch(...)`.

Ignite is not a separate agent framework. It is the component boundary that
turns UI behavior into explicit tools.

## The contract

An Ignite component exposes these runtime methods before any DOM projection
exists:

- `get('schema')` returns immutable catalogue data: known command names after real binding, declared event names, and null unknown runtime schemas. It acquires no source.
- `execute({ command, input? })` runs a command and returns the post-command
  snapshot, derived states, and emitted events from that transition.
- Availability is projected into public states; application tool predicates read it while the source keeps enforcing behavior.
- `get('states')` returns the derived states that renderers, tests, and agents can
  use without reading DOM nodes.
- `on(eventName, handler)` subscribes to public emitted events.
- `watch(handler)` subscribes to derived-states updates over time.

Commands are ordinary typed functions. Explicit application schemas keep model
prompts grounded without requiring metadata from every core author:

```ts
commands: ({ actor }) => ({
  setTemperature: (temperature: number) =>
    actor.send({ type: 'SET_TEMPERATURE', temperature }),
});
```

At the tool boundary, supply `{ commands: { setTemperature: { description: 'Set the thermostat target temperature.', input: { type: 'number', minimum: 58, maximum: 82 } } } }` as the explicit tool schema. The minimal core catalogue does not contain that definition or validate payloads inferred from TypeScript.

## What agents should do

The reliable flow is:

1. Read `get('schema')` for pure discovery, keeping unknown commands distinct from known empty. Bind the actual runtime before expecting callback-derived names.
2. Read `get('states')` for user-facing reasoning; execution results or the caller-owned source provide native snapshots.
3. Supply real application input schemas and tool availability predicates; a core catalogue with null schemas is not enough to create validated model tools.
4. Call `execute({ command, input? })` and inspect the returned `snapshot`,
   `states`, and `events`.
5. Keep long-lived workflows synchronized with `on(...)` for events and
   `watch(...)` for derived states.

That keeps the model out of selector guessing and stale DOM assumptions. The
agent reasons over named commands and typed state transitions.

## Where `igniteTools` fits

`igniteTools(runtime, dialect, { schema, canExecute })` adapts explicit application definitions into provider tools and validated calls. Missing required schemas fail before execution. The source still owns behavior. The
dialect only translates between provider message shapes and Ignite commands.

The smart-home example exercises this split with:

- an XState-backed smart-home runtime,
- an actor-web-backed runtime selected with `SMART_HOME_RUNTIME=actor-web`,
- deterministic scripted-model tests,
- Anthropic tool calls,
- OpenAI-compatible tool calls for local MLX servers,
- a terminal agent and browser UI sharing one live headless runtime.

Run it from
[`examples/agents/smart-home`](https://github.com/0xjcf/ignite-element/tree/beta/examples/agents/smart-home)
to see the contract driven without a DOM first, then shared with a browser UI.

## Ecosystem boundaries

Ignite owns the component contract: commands, derived states, effects,
events, schema, and headless execution.

Provider adapters and examples can turn that contract into model tools, including
OpenAI-compatible local-model calls for MLX. Ignite does not own durable model
serving, process management, or operator setup for MLX. Those belong outside the
component package.

Actor-Web integration follows the same boundary. `ignite-element/actor-web`
projects an Actor-Web runtime and sends explicit requests through a
command-capable source. Ignite does not become the distributed transport,
gateway, or supervision layer.
