A source-backed core works with or without a rendered view.

Agents and tests read derived states, execute commands, and observe events through the headless runtime.

The same core can register a custom element.

The practical model is:

1. Define component behavior and boundaries.
2. Drive workflows through the headless runtime.
3. Offer the same commands with `igniteTools({ core, schema, canExecute?, dialect? })`.
4. Add the DOM layer as a projection over already-proven behavior.

:::note[API reference]
For method signatures, see [Headless runtime](/ignite-element/api/headless-runtime/), [Tools](/ignite-element/guides/tools/), and the [Testing guide](/ignite-element/handbook/testing/).
:::

## Behavior-first components

Start by describing the state source, derived states, commands, events, and effects.

`igniteCore(...)` infers the effect context and command `source` from the configured source and event builder.

Copy [apiShowcaseMachine.ts](https://github.com/0xjcf/ignite-element/blob/beta/examples/adapters/xstate/apiShowcaseMachine.ts) beside this module.

It defines the count, limit, `ADD`, and `SET_LIMIT` behavior used below.

```ts title="agent-counter.ts"
import { apiShowcaseMachine as counterMachine } from './apiShowcaseMachine';
import { igniteCore } from 'ignite-element/xstate';

export const counter = igniteCore({
  source: counterMachine,

  states: (snapshot) => ({
    count: snapshot.context.count,
    limit: snapshot.context.limit,
    isLimited: snapshot.matches('limited'),
    canIncrement: snapshot.can({ type: 'ADD', amount: 1 }),
    canSetLimit: snapshot.can({ type: 'SET_LIMIT', limit: snapshot.context.limit }),
  }),

  commands: ({ source: actor }) => ({
    increment: () => actor.send({ type: 'ADD', amount: 1 }),

    setLimit: (limit: number) => actor.send({ type: 'SET_LIMIT', limit }),
  }),

  events: (event) => ({
    'limit-reached': event<{ count: number; limit: number }>(),
  }),

  effects: ({ snapshot, prevSnapshot, emit }) => {
    if (!prevSnapshot.matches('limited') && snapshot.matches('limited')) {
      emit({
        type: 'limit-reached',
        count: snapshot.context.count,
        limit: snapshot.context.limit,
      });
    }
  },
});
```

That registration gives agents a contract to inspect and a command surface to drive, without the DOM.

This Vitest fragment assumes `counter` is imported from `./agent-counter` and `expect` from `vitest`.

Use a fresh module instance per test and dispose its test-owned core in `finally`.

```ts title="Workflow test (fragment)"
await counter.execute({ command: 'setLimit', input: 6 });
await counter.execute({ command: 'increment' });

expect(counter.get('states')).toMatchObject({ count: 1, limit: 6, isLimited: false });
```

See [Headless runtime](/ignite-element/api/headless-runtime/) for `get`, `watch`, `on`, `execute`, and owning `dispose`.

Projected states such as `canIncrement` are facts for views and for the tools predicate.

They are not themselves the agent gate.

## Offer tools

Keep descriptions and input schemas at the application boundary.

Mark commands `gated: true` and supply `canExecute`.

```ts title="agent-counter-tools.ts"
import { defineToolSchema, igniteTools } from 'ignite-element/tools';
import { openai } from 'ignite-element/tools/openai';
import { counter } from './agent-counter';

export const counterToolSchema = defineToolSchema({
  increment: {
    description: 'Add one to the count.',
    input: { type: 'object', properties: {} },
    gated: true,
  },
  setLimit: {
    description: 'Set maximum count',
    input: { type: 'number', minimum: 3, maximum: 12 },
    gated: true,
  },
});

export const counterTools = igniteTools({
  core: counter,
  schema: counterToolSchema,
  dialect: openai,
  canExecute: (name) => {
    const states = counter.get('states');
    if (name === 'increment') return states.canIncrement;
    if (name === 'setLimit') return states.canSetLimit;
    return false;
  },
});
```

`run` acknowledges the command.

`observe` stays attached while later source work settles.

```ts title="agent-counter-observe.ts"
import { counterTools } from './agent-counter-tools';

const { run, observe } = counterTools;
const subscription = observe((observation) => {
  if (observation.type === 'states') {
    console.log(observation.states);
  }
});
try {
  const result = await run({ name: 'setLimit', input: 6 });
  if (result.ok) {
    console.log(result.value);
  }
} finally {
  subscription.unsubscribe();
}
```

Only offer definitions for commands the core actually exposes.

See [Tools](/ignite-element/guides/tools/) for dialects, tagged errors, and provider loops.

## Add the DOM layer

Once the behavior is stable, the custom element stays thin.

Its renderer consumes derived states and command functions to produce the view.

The default DOM layer uses the public `ignite-element/jsx` runtime and ordinary local style tags.

Machine-backed headless access and each registered element have independent state.

To let an agent drive the same state as a mounted view, pass an existing actor to the core; see [Shared sources](/ignite-element/guides/shared-source-ownership/).

```tsx title="agent-counter-view.tsx"
/** @jsxImportSource ignite-element/jsx */
import { counter } from './agent-counter';

const panelStyles = `
  section {
    display: grid;
    gap: 0.75rem;
    padding: 1rem;
    border: 1px solid color-mix(in srgb, currentColor 15%, transparent);
    border-radius: 1rem;
  }
`;

counter('counter-panel', (ctx) => (
  <section>
    <style>{panelStyles}</style>
    <strong>
      {ctx.count} / {ctx.limit}
    </strong>

    <button type="button" onClick={() => ctx.increment()} disabled={!ctx.canIncrement}>
      Increment
    </button>

    <input
      type="range"
      aria-label="Count limit"
      min={3}
      max={12}
      value={ctx.limit}
      onInput={(event: Event) => {
        if (event.currentTarget instanceof HTMLInputElement) {
          ctx.setLimit(Number(event.currentTarget.value));
        }
      }}
    />

    {ctx.isLimited && <p>Limit reached</p>}
  </section>
));
```

This keeps DOM tests focused on rendering and accessibility, while behavior tests stay selector-free.

To assert rendered controls by role and accessible name, mount the registered component and use DOM Testing Library on its actual rendered elements — see the [Testing guide](/ignite-element/handbook/testing/).

## Ordinary workflow tests

Assert the direct runtime results shown above.

After a command starts asynchronous source work, stay subscribed with `observe` rather than treating `run` as business-done.

Release observers and let the source owner stop native resources.

Logic remains inspectable without the DOM, and the DOM remains a projection over that contract.
