Ignite Element is behavior-first. A source-backed `igniteCore(...)` registration that creates a custom element also exposes a headless runtime, so agents and tests can inspect the contract, execute commands, observe events, and verify derived states before any DOM selector exists.

The practical model is:

1. Define component behavior and boundaries.
2. Test workflows through the headless runtime.
3. Add the DOM layer as a projection over already-proven behavior.

:::note[API reference]
This guide is the narrative walkthrough. For exact signatures and return shapes, see [Headless runtime](/ignite-element/api/headless-runtime/), [Command metadata](/ignite-element/api/command-metadata/), and the [Testing guide](/ignite-element/guides/testing/).
:::

## Behavior-first components

Start by describing the state source, derived states, commands, events, and effects. `igniteCore(...)` infers `snapshot`, `prevSnapshot`, `emit`, `select`, `actor`, and `host` from the `source` plus your `events` builder, so standard authoring needs no internal helper-type imports.

```ts no-check
import { igniteCore } from 'ignite-element/xstate';

export const counter = igniteCore({
  source: counterMachine,

  states: (snapshot) => ({
    count: snapshot.context.count,
    limit: snapshot.context.limit,
    isLimited: snapshot.matches('limited'),
  }),

  commands: ({ actor, command }) => ({
    increment: () => actor.send({ type: 'INCREMENT' }),

    setLimit: command(
      (limit: number) => actor.send({ type: 'SET_LIMIT', limit }),
      {
        description: 'Set maximum count',
        input: command.number({ minimum: 3, maximum: 12 }),
      },
    ),
  }),

  events: (event) => ({
    'limit-reached': event<{ count: number; limit: number }>(),
  }),

  effects: ({ snapshot, prevSnapshot, emit }) => {
    if (!prevSnapshot.matches('limited') && snapshot.matches('limited')) {
      emit({
        type: 'limit-reached',
        count: snapshot.context.count,
        limit: snapshot.context.limit,
      });
    }
  },
});
```

That registration gives agents a contract to inspect and a command surface to drive — all without the DOM:

```ts
counter.getSchema(); // commands + metadata + events + snapshot + states
counter.getStates();   // current derived states
counter.canExecute('increment'); // current command availability

await counter.execute({ command: 'setLimit', input: 6 });

for (let step = 0; step < 20 && !counter.getStates().isLimited; step += 1) {
  await counter.execute({ command: 'increment' });
}

expect(counter.getStates()).toMatchObject({ count: 6, limit: 6, isLimited: true });
```

See [Headless runtime](/ignite-element/api/headless-runtime/) for every method (`execute`, `canExecute`, `getSnapshot`, `getStates`, `getSchema`, `on`, `watchSnapshot`, `watchStates`) and its return shape.

In practice, the loop is:

1. Read `getSchema()` to discover commands, declared events, snapshot, and derived states.
2. Use command metadata input schemas to shape payloads instead of guessing argument structure.
3. Check `canExecute()` when a command is marked as `gated`.
4. Run `execute()` and inspect the returned snapshot, derived states, and emitted events.
5. Keep long-lived observers attached with `on(...)` or `watchStates(...)` when the workflow spans multiple actions.

## Add the DOM layer

Once the behavior is stable, the custom element stays thin — its renderer consumes derived states and command functions to produce the view. The default DOM layer uses the public `ignite-element/jsx` runtime and ordinary local style tags; no project config is required.

```tsx
const panelStyles = `
  section {
    display: grid;
    gap: 0.75rem;
    padding: 1rem;
    border: 1px solid color-mix(in srgb, currentColor 15%, transparent);
    border-radius: 1rem;
  }
`;

counter('counter-panel', ({ count, limit, isLimited, increment, setLimit }) => (
  <section>
    <style>{panelStyles}</style>
    <strong>
      {count} / {limit}
    </strong>

    <button type="button" onClick={() => increment()}>
      Increment
    </button>

    <input
      type="range"
      min={3}
      max={12}
      value={limit}
      onInput={(event) => setLimit(Number(event.currentTarget.value))}
    />

    {isLimited && <p>Limit reached</p>}
  </section>
));
```

This keeps DOM tests focused on rendering and accessibility, while behavior tests stay selector-free. To assert rendered controls by role and accessible name, mount the registered component and use DOM Testing Library on its actual rendered elements — see the [Testing guide](/ignite-element/guides/testing/).

## Agent-readable contracts

Command metadata is optional. Plain functions remain valid commands; `command(fn, metadata)` enriches the runtime schema when an agent or inspector needs more context.

```ts no-check
commands: ({ actor, command }) => ({
  reset: () => actor.send({ type: 'RESET' }),

  renamePreset: command(
    (label: string) => actor.send({ type: 'RENAME_PRESET', label }),
    {
      description: 'Rename the saved preset label.',
      input: command.string({ minLength: 1, maxLength: 32 }),
    },
  ),
});
```

Built-in helpers cover `number`, `string`, `boolean`, `enum`, `object`, and `array` while staying JSON-serializable, and `getSchema()` returns executable commands plus their metadata in one map. The full helper catalog and the serialized schema shape live in [Command metadata](/ignite-element/api/command-metadata/).

Availability predicates live on the same command metadata but stay off the JSON
schema. They are evaluated against the current snapshot by the headless runtime:

```ts no-check
commands: ({ actor, command }) => ({
  submit: command(
    () => actor.send({ type: 'SUBMIT' }),
    {
      description: 'Submit the current form.',
      canExecute: ({ snapshot }) => snapshot.can({ type: 'SUBMIT' }),
    },
  ),
});

counter.getSchema().commands.submit.gated; // true
counter.canExecute('submit');              // boolean for the current snapshot
```

That means an agent or provider can keep the contract discovery step pure and JSON-safe, then defer the live authorization question to `canExecute()` immediately before invocation. The full runtime example is in [`getSchema()`](/ignite-element/api/headless-runtime/#getschema).

## Ordinary workflow tests

Assert the direct runtime results shown above, preserving source-owned asynchronous outcomes and real DOM coverage. Replace unbounded loops with an application-specific step limit; after a command starts asynchronous source work, wait on its correlated source state/event rather than assuming `execute()` completes it. Release observers and let the source owner stop native resources.

The former recorder, trace helpers, story snapshots and lifecycle histories are intentionally retired without a replacement recorder. See the [migration notice](/ignite-element/api/testing-dsl/). Logic remains inspectable without the DOM, and the DOM remains a projection over that contract.
