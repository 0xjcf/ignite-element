Ignite Element v3 moves component authoring toward a behavior-first workflow. The same `igniteCore(...)` registration that creates a custom element also exposes a headless runtime so agents and tests can inspect the component contract, execute commands, observe events, and verify projected view state before any DOM selector is involved.

The practical model is:

1. Define component behavior and boundaries.
2. Test workflows through the headless runtime.
3. Add the DOM layer as a projection over already-proven behavior.

## Behavior-first components

Start by describing the state source, projected view, commands, events, and effects.

```ts
import { igniteCore } from 'ignite-element/xstate';

export const counter = igniteCore({
  source: counterMachine,

  view: ({ snapshot }) => ({
    count: snapshot.context.count,
    limit: snapshot.context.limit,
    isLimited: snapshot.matches('limited'),
  }),

  commands: ({ actor, command }) => ({
    increment: () => actor.send({ type: 'INCREMENT' }),

    setLimit: command(
      (limit: number) => actor.send({ type: 'SET_LIMIT', limit }),
      {
        description: 'Set maximum count',
        input: command.number({ minimum: 3, maximum: 12 }),
      },
    ),
  }),

  events: (event) => ({
    'limit-reached': event<{ count: number; limit: number }>(),
  }),

  effects: (snapshot, prevSnapshot, { emit }) => {
    if (!prevSnapshot.matches('limited') && snapshot.matches('limited')) {
      emit('limit-reached', {
        count: snapshot.context.count,
        limit: snapshot.context.limit,
      });
    }
  },
});
```

This gives agents a contract they can inspect:

```ts
counter.getSchema();
counter.getState();
counter.getView();
```

And a command surface they can drive:

```ts
await counter.execute('setLimit', 6);

while (!counter.getView().isLimited) {
  await counter.execute('increment');
}

expect(counter.getView()).toMatchObject({
  count: 6,
  limit: 6,
  isLimited: true,
});
```

## Add the DOM layer

Once the behavior is stable, the custom element can stay thin. It consumes projected view values and command functions.

```tsx
counter('counter-panel', ({ count, limit, isLimited, increment, setLimit }) => (
  <section>
    <strong>
      {count} / {limit}
    </strong>

    <button type="button" onClick={() => increment()}>
      Increment
    </button>

    <input
      type="range"
      min={3}
      max={12}
      value={limit}
      onInput={(event) => setLimit(Number(event.currentTarget.value))}
    />

    {isLimited && <p>Limit reached</p>}
  </section>
));
```

This keeps DOM tests focused on rendering and accessibility, while behavior tests stay selector-free.

## DOM accessibility bridge

When the behavior contract is already proven, mount the same runtime behind a test-only DOM bridge and assert the rendered controls by role and accessible name.

```ts
import { test as igniteTest } from "ignite-element/xstate";

const story = counter.record("reaches limit");
const bridge = igniteTest.accessibilityBridge(
  counter,
  ({ count, limit, isLimited, increment, setLimit }) => (
    <section>
      <output role="status" aria-label="Counter status">
        {count} / {limit}
      </output>

      <button type="button" onClick={() => increment()}>
        Increment
      </button>

      <label>
        Limit
        <input
          type="range"
          min={3}
          max={12}
          value={limit}
          onInput={(event) => setLimit(Number(event.currentTarget.value))}
        />
      </label>

      {isLimited && <p role="status">Limit reached</p>}
    </section>
  ),
  { elementName: "counter-accessibility-bridge" },
);

await story.execute("setLimit", 6);
await story.until((view) => view.isLimited, async () => {
  await story.execute("increment");
});

igniteTest.expectControls(bridge, [
  { role: "status", name: "Counter status", text: "6 / 6" },
  { role: "button", name: "Increment" },
  { role: "slider", name: "Limit", value: "6" },
  { role: "status", name: "Limit reached" },
]);

bridge.stop();
story.stop();
```

`igniteTest.accessibilityBridge(...)` renders against the same runtime state that `story.execute(...)` mutates, so behavior assertions remain headless while DOM assertions stay focused on projection proof. `igniteTest.expectControls(...)` keeps those DOM checks small: match the rendered control by role, accessible name, text, or value instead of rebuilding the whole story trace around selectors.

## Agent-readable contracts

Command metadata is optional. Plain functions remain valid commands, and `command(fn, metadata)` enriches the runtime schema when an agent or inspector needs more context.

```ts
commands: ({ actor, command }) => ({
  reset: () => actor.send({ type: 'RESET' }),

  renamePreset: command(
    (label: string) => actor.send({ type: 'RENAME_PRESET', label }),
    {
      description: 'Rename the saved preset label.',
      input: command.string({ minLength: 1, maxLength: 32 }),
    },
  ),

  setLimit: command(
    (limit: number) => actor.send({ type: 'SET_LIMIT', limit }),
    {
      description: 'Set maximum count',
      input: command.number({ minimum: 3, maximum: 12 }),
    },
  ),

  configureAlerts: command(
    (payload) => actor.send({ type: 'CONFIGURE_ALERTS', payload }),
    {
      description: 'Update alert routing rules.',
      input: command.object(
        {
          enabled: command.boolean({ default: true }),
          priority: command.enum(['low', 'high'], { default: 'low' }),
          channels: command.array(command.string(), { minItems: 1 }),
        },
        { required: ['enabled', 'priority', 'channels'] },
      ),
    },
  ),
});
```

Built-in helpers cover `number`, `string`, `boolean`, `enum`, `object`, and `array` metadata while staying JSON-serializable.

`getSchema()` returns executable commands and command metadata in one map.

```ts
{
  commands: {
    reset: {},
    renamePreset: {
      description: 'Rename the saved preset label.',
      input: { type: 'string', minLength: 1, maxLength: 32 },
    },
    setLimit: {
      description: 'Set maximum count',
      input: { type: 'number', minimum: 3, maximum: 12 },
    },
    configureAlerts: {
      description: 'Update alert routing rules.',
      input: {
        type: 'object',
        properties: {
          enabled: { type: 'boolean', default: true },
          priority: { type: 'string', enum: ['low', 'high'], default: 'low' },
          channels: {
            type: 'array',
            items: { type: 'string' },
            minItems: 1,
          },
        },
        required: ['enabled', 'priority', 'channels'],
      },
    },
  },
  events: ['limit-reached'],
  state: { value: 'active', context: { count: 0, limit: 6 } },
}
```

## Story recording

Stories make behavior workflows first-class. A recorder captures command, event, state, and projected view changes as one behavior trace, while DOM lifecycle evidence stays available through a separate lifecycle channel on the same story object.

```ts
import { test as igniteTest } from "ignite-element/xstate";

const story = counter.record("reaches limit");

await story.execute("setLimit", 6);
await story.until((view) => view.isLimited, async () => {
  await story.execute("increment");
});

const trace = igniteTest.serializeTrace(story.trace());
const snapshot = igniteTest.snapshotStory(story);
const lifecycle = story.lifecycle();
const summary = story.summary();

expect(summary.finalView).toMatchObject({
  count: 6,
  limit: 6,
  isLimited: true,
});

igniteTest.expectTrace(trace, [
  { kind: "command", command: "setLimit", payload: 6 },
  { kind: "event", event: "limit-reached", payload: { count: 6, limit: 6 } },
  { kind: "view", phase: "after", view: { isLimited: true } },
]);

expect(snapshot).toMatchInlineSnapshot();

story.stop();
```

`igniteTest.serializeTrace(story.trace())` returns a deterministic JSON-safe snapshot shape: ordered entries with `kind`, `sequence`, `step`, and the relevant `command`, `event`, `phase`, `payload`, `state`, or `view` fields. That makes it suitable for snapshot tests, reporter output, or Playwright assertions without requiring DOM selectors. `igniteTest.expectTrace(...)` matches ordered checkpoints instead of forcing brittle full-array equality.

`story.trace()` intentionally contains only behavior evidence: command, state, view, and event entries. `story.lifecycle()` contains DOM evidence such as registration, connection, render, disconnection, and cleanup when custom elements or accessibility bridges are active during the story. If no DOM projection participates, `story.lifecycle()` returns an empty array.

## Gaps to close

The current v3 runtime supports `execute()`, `getState()`, `getView()`, `getSchema()`, `on()`, `watch()`, `watchView()`, `record()`, ordered workflow trace assertions, and serializable story snapshots. The remaining gaps are the pieces needed to turn those primitives into a complete agent workflow system.

- Schema semantics: the runtime now ships JSON-serializable helpers for `number`, `string`, `boolean`, `enum`, `object`, and `array` inputs; future work can add higher-level conventions such as examples, UI hints, or shared vocabularies if agents need them.
- DOM bridge: now available through `igniteTest.accessibilityBridge(...)` and `igniteTest.expectControls(...)`; future work can extend the accessible-query vocabulary if agents need richer semantics than role, name, text, and value.

The important boundary is that logic stays inspectable without the DOM, and the DOM remains a projection over the tested contract.
