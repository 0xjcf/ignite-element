The flow is **source → native snapshot → states → renderer view**. One existing
source can serve multiple views. No controller, source descriptor or mandatory
shell is needed. Each application process owns its instances; sharing code does
not synchronize devices.

For version-specific hook preparation and terminal-disposal behavior, read the
[beta.13 migration note](/ignite-element/migration/shared-readiness-terminal-disposal/).
The examples below keep established public inputs and inline inferred callbacks.

## Ownership is explicit without another API

| Source input | Ownership |
| --- | --- |
| Existing XState actor | Application-owned; Ignite releases only its observation resources |
| XState machine definition | Existing Ignite acquisition creates private isolated actors and owns their release |
| Existing Redux store or MobX observable | Application-owned behavior, using `ignite-element/redux` or `ignite-element/mobx` and native operations |
| Actor-Web source | Separate optional runtime; native authority stays with Actor-Web/application |

The root `igniteCore()` is still source-free and registrar-only. New source
factories and ownership descriptors are not part of this correction.

Navigation removes observers, not the feature's source. Source-native sign-in,
sign-out and account reset can keep one core and its registrations. At final
application shutdown, dispose the core and separately stop a borrowed actor:

```ts
import { createActor, createMachine } from 'xstate';
import { igniteCore } from 'ignite-element/xstate';

const source = createActor(createMachine({})).start();
const core = igniteCore({ source });
try {
  core.dispose();
} finally {
  source.stop();
}
```

This is two ownership operations, not an Ignite shutdown wrapper. Existing private
acquisition paths keep their adapter's established release policy. Repeated core
disposal does not repeatedly release resources. Application-owned observations
are outside the core's custody.

## React and React Native

<Code code={reactCode} lang="tsx" title="React shared counter" />

Shared cores are ready after owner-controlled construction. Unmounting a view
releases its subscription, not the core. One effect evaluator per core/source
instance starts on legitimate runtime use or committed subscription/element
connection, establishes an initial baseline, and queues delivery after source
processing. The activated shared evaluator survives zero-view intervals until
core disposal; delivery does not guarantee a renderer update or framework commit.
See [delivery and ownership](/ignite-element/handbook/events/#delivery-and-ownership)
for the canonical activation, lifetime, disposal, synchronous-void and error rules.

## Source-owned account and receipt behavior

The synthetic preference source owns account identity and a generation. Sign-out
clears private state and exits its invocation; an old intent carries an old
generation and is rejected. A new account uses the same actor/core, not rebinding.

<Code code={sourceCode} lang="ts" title="shared-session.ts" />

The receipt actor lives above `pending` and `unknown`. A native XState deadline
does not discard a later confirmation while that operation is live. Account and
generation checks reject mismatched receipts. A transport error is unknown, not a
confirmed rejection or permission to retry. Ending local observation or exiting
a source state does not undo backend work already accepted.

<Code code={viewCode} lang="tsx" title="shared-session-view.tsx" />

The view sends one intent from `ctx`; it does not orchestrate completion or repeat
projection logic. Generation is a genuine correlation fact, not a second command
registry. Ports belong to the source's native actor input. Tests inject
`SimulatedClock` directly, with no timer adapter.

Retain source-side business eligibility, authentication, receipt validation and
remote cancellation in a real application. These synthetic rules are not Ignite
authorization. Existing plain TypeScript controllers remain supported through the
[advanced interoperability recipe](/ignite-element/guides/plain-controllers/).
