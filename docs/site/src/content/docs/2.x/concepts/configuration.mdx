The default v3 path does not need `ignite.config.ts`: use Ignite JSX, set `jsxImportSource: "ignite-element/jsx"`, and keep component CSS in local `<style>` tags.

Use `ignite.config.ts` only when you need advanced `ignite-renderer` compatibility for shared shadow-root styles, diagnostics, strategy overrides, or the legacy `lit` renderer.

```ts
// ignite.config.ts
import { defineIgniteConfig } from 'ignite-renderer';

export default defineIgniteConfig({
  styles: new URL('./styles.css', import.meta.url).href, // injected into each shadow root
  logging: 'warn', // "off" | "warn" | "debug"
  // renderer: 'lit',
  // strategy: 'replace',
});
```

### Loading the config

* The default `ignite-element` public API does not auto-load config files.
* If you maintain legacy auto-loading, treat that bundler wiring as internal compatibility behavior.
* Otherwise import your config in your app entry before you register components.

Default behavior:

* If config is absent, Ignite uses config-free Ignite JSX.
* If config exists but `renderer` is not set, Ignite still defaults to `ignite-jsx`.
* Invalid configured renderer values are normalized by legacy compatibility behavior and logged; avoid relying on that path.

### Scoped vs. global styles

Component-local `<style>` tags are the default scoped styling path. The config `styles` URL is for shared styles that should be injected into each component shadow root. Add light-DOM styles in your host app as usual.

### Per-component overrides

Renderer and strategy overrides are intended to be project-wide advanced settings. Per-component render strategy overrides are internal and not part of the public API.
