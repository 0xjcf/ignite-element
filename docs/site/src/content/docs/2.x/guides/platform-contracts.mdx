Ignite helps you keep behavior explicit, but it does not replace the browser contract. Good Ignite components still need good HTML, clear events, stable styling hooks, and accessibility semantics.

## Semantics live in your markup

Use real platform elements first:

* Prefer `<button>`, `<input>`, `<label>`, `<dialog>`, and `<form>` over generic `<div>` wrappers.
* Keep labels, names, and interactive affordances in the rendered markup.
* Reflect derived state with DOM attributes or `aria-*` when that state matters to assistive technology.

Ignite keeps logic out of the renderer. It does not invent semantics for you.

## Commands stay internal, events go outward

Inside Ignite, `commands` are the renderer-facing intent API. Outside Ignite, host apps should integrate through DOM events and the custom element boundary.

```ts
events: (event) => ({
  saveSucceeded: event<{ id: string }>(),
  saveFailed: event<{ message: string }>(),
}),
effects: (snapshot, _prevSnapshot, { emit, select }) => {
  const status = select((current) => current.context.status);
  const error = select((current) => current.context.error);

  if (status.changed && status.current === 'saved') {
    emit('saveSucceeded', { id: snapshot.context.id });
  }

  if (error.changed && error.current) {
    emit('saveFailed', { message: error.current });
  }
},
```

Good event contracts are:

* stable
* named for business meaning, not framework mechanics
* emitted from `effects`, not from view code
* documented as part of the public element surface

## Styling is part of the contract

Use the shadow root for implementation details, then deliberately expose the styling hooks host apps are allowed to depend on:

* CSS custom properties for design tokens
* `part` attributes for targeted shadow-root styling hooks
* light-DOM layout styles in the host app

```tsx
component('status-chip', ({ label, tone }) => (
  <span
    part="chip"
    class={`chip chip--${tone}`}
    style={{ color: 'var(--status-chip-fg, currentColor)' }}
  >
    {label}
  </span>
));
```

If you expect host apps to theme a component, expose a stable token or part. If you do not want a sub-tree styled externally, keep it internal.

## Accessibility is not optional

Use this checklist for every public component:

* Interactive controls use native interactive elements where possible.
* Focus states are visible.
* Icon-only UI has an accessible name.
* Derived state that matters externally is reflected with `aria-*`, text, or both.
* Events communicate business outcomes, not just implementation details.

For example, a state change might update `aria-pressed`, button text, and emit `toggled` from the same transition.

## Keep the contract browser-native

The strongest Ignite components behave predictably across hosts because they rely on platform primitives:

* HTML for structure
* Shadow DOM for encapsulation
* `CustomEvent` for outward signals
* CSS variables and `part` for theming hooks
* framework wrappers only as optional adapters

If a host app cannot consume your component without framework-specific glue, the public contract is probably too framework-shaped.
