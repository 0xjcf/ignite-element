This guide is for applications using stable v2.

For a new project, start with [Getting started](/ignite-element/).

:::caution[v3 is in beta]
Install v3 through `@beta`.

The stable `ignite-element@latest` package remains v2.2.2.
:::

## Install the beta

Install Ignite with the source library your application uses:

```sh title="Terminal"
pnpm add ignite-element@beta xstate
```

For Redux, replace `xstate` with `@reduxjs/toolkit`.

For MobX, replace it with `mobx`.

State libraries and `lit-html` are optional peers in v3.

The facade installs its internal `@ignite-element` packages automatically.

Keep importing `igniteCore` from the entrypoint for your source, such as `ignite-element/xstate`.

## Use ES modules

v3 is native ESM-only.

Replace CommonJS `require` calls with ES module imports.

See [Compatibility](/ignite-element/api/compatibility/) for supported toolchains and declaration-resolution limits.

## Update command callbacks

The v2 command context exposed `actor`, `emit`, and `host`.

In v3, commands receive `source`, the active instance's command interface.

For a callback that only sends an XState event, update it as follows:

```diff
- commands: ({ actor }) => ({
-   toggle: () => actor.send({ type: "TOGGLE" }),
+ commands: ({ source }) => ({
+   toggle: () => source.send({ type: "TOGGLE" }),
  })
```

Pass presentation-specific values as command arguments instead of reading `host` in the callback.

Move outward event production out of commands.

Use native source events for occurrences and effects for notifications derived from state changes.

The [command emission guide](/ignite-element/migration/effects-events/) shows how to preserve command input and repeated occurrences.

Keep `states` for derived values; v2 already supported this callback.

See [Sources](/ignite-element/handbook/sources/) for each adapter's snapshot and command shapes.

## Update configuration imports

The v2 `ignite-element/config/*` and `ignite-element/renderers/*` entrypoints are not public v3 entrypoints.

Remove `igniteConfigVitePlugin()` or `IgniteConfigWebpackPlugin` from your bundler setup.

The v3 public API does not include these config-loader plugins.

For Ignite JSX, use the compiler settings and component-local CSS shown in [Getting started](/ignite-element/).

If your `ignite.config.ts` only selected the default JSX renderer, remove that file and its imports.

Preserve any shared stylesheet or renderer settings your application still needs.

For those settings, import `defineIgniteConfig` from `@ignite-element/renderer` and load the settings module explicitly before registering components.

The filename `ignite.config.ts` has no special loading behavior in v3.

For Lit, import `@ignite-element/renderer/lit` before registering components.

See [Advanced configuration](/ignite-element/api/advanced-config/) for the required dependencies and complete setup.

## Check behavior and ownership

Run TypeScript checks and the application's behavior and DOM tests.

Verify declared events, their payloads, and listeners using [Events & effects](/ignite-element/handbook/events/).

Keep source construction and native shutdown at the application boundary.

Use [Ownership & cleanup](/ignite-element/handbook/ownership/) to review shared sources, isolated instances, and terminal disposal.

The [Testing guide](/ignite-element/handbook/testing/) shows source, core, and rendered-control assertions.
