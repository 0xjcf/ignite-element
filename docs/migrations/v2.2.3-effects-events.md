# Migration Guide: effects-based events

Ignite Element now treats `commands` as intent triggers and `effects` as the place where state transitions produce DOM events. This guide shows how to migrate existing components that still call `emit()` inside `commands()`.

## Summary

Before:

- `commands({ actor, host })`
- command bodies both updated state and emitted DOM events

After:

- `commands({ actor, host })`
- `effects(snapshot, prevSnapshot, { emit, actor, host })`
- effects emit only when the relevant transition actually happened

## Before / after

Before:

```ts
const registerToggle = igniteCore({
  source: machine,
  events: (event) => ({
    toggled: event<{ isOn: boolean }>(),
  }),
  commands: ({ actor }) => ({
    toggle: () => {
      actor.send({ type: "TOGGLE" });
    },
  }),
});
```

After:

```ts
const registerToggle = igniteCore({
  source: machine,
  events: (event) => ({
    toggled: event<{ isOn: boolean }>(),
  }),
  commands: ({ actor }) => ({
    toggle: () => {
      actor.send({ type: "TOGGLE" });
    },
  }),
  effects: (snapshot, prevSnapshot, { emit }) => {
    if (snapshot.matches("on") === prevSnapshot.matches("on")) return;
    emit("toggled", { isOn: snapshot.matches("on") });
  },
});
```

## Migration steps

1. Remove `emit` from the `commands` parameter list.
2. Keep each command limited to actor/store/observable intent.
3. Add an `effects` callback.
4. Compare `snapshot` and `prevSnapshot` so each event fires only on the intended transition.
5. Keep using the existing `events` map so `emit` stays typed.

## Scripted assist

Run the migration helper from the repo root:

```bash
node scripts/migrate-emit-to-effects.mjs
```

It scans the repo for:

- command contexts that still destructure `emit`
- `emit(...)` call sites that likely need to move into `effects()`

You can also write the report to a file:

```bash
node scripts/migrate-emit-to-effects.mjs --report .fas/artifacts/effects-migration-report.txt
```

The helper is intentionally non-destructive. It produces a migration report instead of rewriting code blindly.

## Breaking release note

`emit` has been removed from command context. Commands now receive `{ actor, host }` only, and typed event emission belongs in `effects()`.

## Release boundary

- Migration docs/tooling remain available to help remove old command emit patterns.
- `effects()` is now the supported path for typed event emission.

## Why this matters

- Commands become easier to reason about because they express intent only.
- Effects become deterministic and replay-friendly because they derive from state transitions.
- The headless runtime (`execute`, `getState`, `subscribe`) can report emitted events consistently across UI and automation flows.
